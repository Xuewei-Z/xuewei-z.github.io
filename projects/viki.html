Viki — an AI agent for the whole company's Slack

An internal Slack agent that answers questions from company-wide knowledge, connected to several sources: code, tickets, chat, docs, and design files.

Viki is an internal company tool, so this page stays high-level: no internal data, code, or screenshots.

The problem

Teams work across U.S. and international time zones. Finding out who owns a project, or where it stands, usually meant asking in chat and waiting hours for a reply. The answer already existed, but it was spread across several tools.

What I built

  • Agent core: native tool calling with a bounded 3-round re-planning loop and a latency budget, so the agent can try again without running forever.
  • Memory: session memory with query rewriting, so follow-up questions like "and who reviewed it?" make sense.
  • Grounded answers: two-stage RAG with an explicit "I don't know" fallback. Citations come only from retrieved data, so the agent can't invent links.
  • Team workflows: leads @mention Viki in channels to recap discussions and turn meeting notes into Linear tickets.
  • Safe actions: tools exposed through an MCP server, as the base for human-approved actions.

How it evolved

I started with the smallest, cheapest test, and scaled up only after each step proved the idea worked.

Local MVP · Ollama → Cloud GPU · vLLM → Production · Azure
  • Local MVP (Ollama): a 4B model on my own machine, to check whether the approach worked at all, at almost no cost.
  • Cloud GPU (vLLM): a 4B model served on a cloud GPU, so multiple users could use it at the same time.
  • Production (Azure): DeepSeek-V4-Flash on Azure AI Foundry, with GPT-4.1-mini as a second candidate. The app runs 24/7 on an Azure VM, with a 45-second per-call timeout and a 90-second request budget.

Logging every question

Every question is written to a SQLite log: the rewritten query, the routing decision, retrieved sources, the answer, its outcome, and the tokens and latency of each step. Two design choices keep the data honest:

  • Router and answer costs are stored separately, so a change in routing isn't hidden by the answer numbers.
  • Facts and judgements live in separate tables, and raw answers are kept untouched, so any outcome can be recomputed later.

How I measured it

I designed and maintain the evaluation harness. Typed question sets check each answer against expected sources and required or forbidden content. Routing is scored step by step, separately from answer quality, and every release must pass a 16-question regression set.

On top of that, I query the log with SQL to find what tests alone can't show:

  • Outcome rates: how often Viki answered, found no context, errored, or timed out.
  • Regression or capability gap: when failures rose, unrewritten questions failed 80% of the time and rewritten ones 64%, so query rewriting wasn't the cause. The full history showed those question types had never succeeded: a capability gap, not a regression.
  • Latency: identical routing calls ranged from 1.4 to 87.8 seconds. The cause was Azure's shared capacity, not Viki's own traffic.

What didn't work

Retrieval-score confidence looked like an easy way to decide when an answer was trustworthy. I tested it before building on it and found it unreliable, so I dropped it.

Shipping it

Viki runs as a systemd service on the VM. CI runs linting and tests on every change, and the VM pulls and deploys only commits that pass. Each deploy runs a health check and rolls back automatically if it fails.
